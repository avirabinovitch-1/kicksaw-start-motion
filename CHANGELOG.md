# Changelog

## 0.2.0 (not released; on branch agents-0.2.0, written Nov 10, 2026, not yet tested)

Agents (Avi, Nov 9 and 10). Eight agents in `plugins/start-motion/agents/`, each with one job, a cold start and a fixed answer shape, started by the stage commands. Version numbers in plugin.json and marketplace.json are not bumped until the tests in the project doc `claude/agents-test-handoff-2026-11-10.md` have run.

- Source checker and story reviewer. `/discovery-call` runs both on the rows and stories a call added or changed (new step 4b), and `/user-stories` runs both on an epic's stories before the SC sees them and the story reviewer again before a story the SC edited goes to Jira. Plainly wrong things the transcript settles are fixed (a quote that differs from the transcript, a wrong timestamp, a missing trigger the client stated); a requirement found narrower or broader than what the client said is never reworded on its own and goes to the SC with the source lines beside it. Two passes at most. Reports say whether the reviewers ran as separate agents or as a second pass.
- Org reader and design reviewer. `/design` starts from the org summary when the client has an org, and has the design checked for uncovered requirements, conflicts with the org and anything beyond the confirmed scope (new step 4b).
- New command `/start-motion:build-plan`: approved stories and the approved design become ordered build tasks in `docs/build-plan.md` in the client's repo. The SA approves it.
- New command `/start-motion:build`: one task at a time. Test writer (when the task has code), builder, then the story compliance reviewer and the Salesforce quality reviewer; three rounds at most, then a person. Ends in a pull request with its evidence and an evidence note on the Jira story. Agents validate against the sandbox and never deploy; a deploy of merged work to the sandbox runs only on a person's word.
- Guardrails (Avi, Nov 10). Agents never delete anything from an org, records or metadata; a removal is a named task that the person confirms and carries out by hand, and the builder only takes the item out of the repo. Nothing runs against production: the build stage has no override, and the org reader reads a production org only after the person says so plainly, naming the org. A deploy of merged work to the sandbox is read back and confirmed first. An org guard hook (`hooks/org-guard.sh`) blocks record commands, anonymous Apex, direct API calls, destructive deploys, org deletion and package uninstalls, and makes every saving deploy wait for the person's own confirmation.
- Deploy and undo (Avi, Nov 10). The builder validates; once a task has passed both reviews `/build` asks whether to deploy it to the sandbox so the by-hand checks can happen before the merge, one confirmation per deploy. A rejected, unmerged task is taken back out with "undo <task ID>": a fixed script (`skills/build/scripts/undo-task.sh`) lists from git what that task created and changed, the guard re-checks the list and that the org is a sandbox, and the person confirms. Merged work is never undone this way.
- Guard, revised (Avi, Nov 10). Queries about configuration pass; a query that returns client records asks the person first; writes, loads, exports and deletes of records stay blocked. The guard asks the CLI what kind of org an alias is and refuses any saving deploy or removal aimed at an org that is not a sandbox.
- Reviewer fixes also apply to rows and stories the SC has edited (Avi, Nov 10): only what the finding names changes, each change is listed for the SC, and a reviewed story goes back to Draft.
- Simple and sound (Avi, Nov 10). `/design` has a new section 3b: only what the scope needs, standard before custom, configuration before code, one copy of every fact (a lookup or a formula before a flat field that repeats another record, with the cases where a flat field is right), one automation per object and event, access through permission sets, nothing removed quietly. The design reviewer and the Salesforce quality reviewer check the same list; the builder builds the simplest thing that satisfies the criteria and raises a heavier design as a suggestion.
- Easier to act on. The source checker reads each call once, separates citation fixes from findings, marks each finding clear or a judgment call and names the few words that would make the row match. The story reviewer separates what stops the build from what is tidy. Reports put the clear findings first and name a single cause when one call throws many. A pull request opens with what it does, what to check before merging and what to decide. The org summary opens with ten lines at a glance. UAT scripts are grouped into short scenarios with a time estimate.
- Every skill that starts an agent carries a copy of it at `references/agents/`, written by `scripts/sync-agents.py`, for sessions that cannot start a separate agent.
- Decisions (Avi, Nov 10). Every design and build choice with a real alternative gets a row on a new Decisions tab of the requirements list: the question, the options with their trade-offs, Claude's pick or lean, what was chosen, why, what would change it, who decided, when and where. Four kinds: Clear (Claude decides, logs it and moves on; the SA can reopen any, and approving the design accepts the rest), Recommended (the work goes ahead on Claude's pick; the SA confirms before the design goes Final or a dependent task is approved), SA call (options side by side, the section stays Open, everything else is drafted) and Client call (an Open items question for the SC; closes when a call or refinement answers it). A decision never stops a run: only the work that depends on it waits. A changed decision is a new row and the old one is Superseded. Standard in `plugins/start-motion/shared/decisions.md`, copied into design, build-plan and build.
- Decision picker. In Claude chat, the open decisions are put to the SA in one clickable picker (`shared/decision-picker.html`): option cards with the trade-offs and Claude's lean, a write-your-own option, Confirm or Change on each recommendation, and Reopen on the calls Claude made. Anything left unpicked stays open. Elsewhere, the same in a plain text block answered in one line. Shown at the end of `/design`, at build plan approval, and when a build task is handed back on a decision.
- Decisions carried through. `/design` logs every choice as it drafts, writes a client-readable Key decisions section, marks Recommended and Open sections with their IDs, and will not go Final with an SA call or recommendation still open. The design reviewer is handed the decided rows, does not flag a choice they record, and reports work that contradicts one and choices nobody logged. `/build-plan` marks tasks that wait on an open decision and plans the rest, and adds a Build plan block (tasks, decisions, what it waits on) under the SA's own Build/Solution Details text in Jira. The builder and the Salesforce quality reviewer are handed the decided rows; when the builder needs a decision it writes it as an options brief, `/build` logs it as an SA call, hands back only that task and its dependents, and builds the rest. `/discovery-call` and `/user-stories` refinement close a decision row when they close its Open items question.
- Built work on the Jira story (Avi, Nov 10). The story's Metadata field lists every component merged for it, one `Type/Member` per line in the form HLS already uses, generated from git by `skills/build/scripts/metadata-list.py` (list, merge, drop) and never typed by hand; lines a person added stay. Removals go in Build/Solution Details, not Metadata. Commits and pull request titles start with the Jira key so they show on the story's Development panel; Deployment URL gets the story's pull requests link unless it holds another tool's link; Build Environment is set to the sandbox's kind when a task is deployed to it, never Production; Test Steps gets the UAT script's steps once the SC has read it. Fields are found by name on each project and never written where they do not exist. Acceptance Criteria Validated?, Testing Feedback and status stay the tester's and the team's.
- Design and build review page (Avi, Nov 10). One page per client build for the SA, modeled on Ben Bolding's Fred Hutch epic designs in Notion, with diagrams: Needs you, stories served, where the design differs from the stories, rules (decided rows) with who decided, today and after, a data model diagram drawn from the relationship fields, a diagram per flow, automation with what already runs beside it, every component (objects, fields, rules, flows, pages, actions, list views, permission sets) with its details read from the metadata files, story, task, decision and status, a permission matrix for objects and new fields, changes to what exists, the build, open questions, checks, not built, sources and change log. It finds on its own new fields or objects no permission set grants, two active flows on the same object and moment, and components the plan does not name. `/build-plan` makes it for the SA to approve the plan from; `/build` updates it after every pull request, merge and undo, at the same link. `shared/build-review.py` (copied into both skills' scripts), standard in `shared/build-review.md`. Harborlight example: https://claude.ai/artifact/45C1mKqt45KW24HsKmsuMY
- Decision picker, revised for the accountable SA (Avi, Nov 10). Each SA call shows why it matters, the requirement, the client's own words, what the org has today and what it holds up; each option shows what it builds, a small picture of its data model, pros, cons, risk, effort and whether it is easy to change later, with Claude's lean and what would change it. The SA can decide, write their own, or say "I need more first" with what they need, and give a reason for the log. Recommendations are no longer pre-confirmed: each is confirmed, changed or questioned (Confirm all is one click), and shows what has already been built on it. Client calls take an optional lean; Claude's calls show their reason and can be reopened. At build plan approval the picker carries the approval itself, and links to the review page. Every fact in it must come from a source the SA could check.
- Solution map (Avi, Nov 10): building one epic at a time without boxing in the next. `/design` covers every epic in the signed scope and carries a Solution map: every object with the epics that use it, one automation owner per object and moment with the epics that add branches to it, shared values, record types, sharing, permission set structure and naming, and the structural questions several epics depend on (decided before the first of them is planned). The rule: build only what an epic needs, in the shape the whole map calls for. `/build-plan` reads the other epics' requirements for every object it touches before planning, plans shared pieces once as foundation tasks, logs any choice that would close a door on a later epic as an SA call, stops for an object the map does not cover, and notes on each task the later epics that build on it. The builder and the Salesforce quality reviewer are handed the map rows (a second flow where the map names one owner is a must-fix); the design reviewer gets the later epics' requirements and reports what closes a door. The review page shows an Across the whole solution table and draws later-epic objects dashed in the data model.
- Review page simplified to Ben's style (Avi, Nov 10): plain document, stories first, Open for the SA only while anything is open, decided rows as a numbered list with what else was considered and who decided, rebuilt after every decision so that once the SA is through everything it reads as the finished design. Picker cleaned up: no mini diagrams, plain values, API names only as code.
- `/build` catches up on its own: at the start of every run it finds pull requests merged since the last run, sets them Merged and updates their stories. A run of several tasks no longer stops at the first task that needs a person: that task is handed back, its dependents are skipped and listed, and the rest are built, with everything waiting on a person reported in one place.
- Design, readout and review page live in Drive (Avi, Nov 11). These are client records, so none lives only in one person's Claude account. The master copy of each is an HTML file in the client's Drive folder (`Design`, `Readout`, `Build` subfolders), one running document saved as a new file per version, with the previous version moved to `Older versions` and never trashed; a PDF of each version sits beside it because Drive cannot preview HTML. The Claude link is the view and is republished from the Drive file; anyone can republish it if the original owner cannot. `/design` reads the current version from Drive at the start of every run, versions v0.x as a draft, v1.0 at Final and v1.1 and up after, keeps a change log, and at Final also commits `docs/solution-design.html` to the repo. The readout keeps working from the SC's project and saves every built version to Drive, and a run picking it up from someone else starts from the Drive copy. Standard in `shared/drive-copies.md`.
- Process context for the build (Avi, Nov 11). `/build-plan` reads the workflows in scope and the signed readout, writes the workflow step each task serves onto the task in one line, and follows a fixed order when sources disagree: the story's criteria and Build/Solution Details, then Decided rows, then the design at the version the plan names, then the signed readout, then the workflows. The readout and workflows never add scope, and every disagreement is listed for the SA. The builder gets only the task's workflow line, never the documents, and builds to the criteria when the two differ. The design reviewer is handed the workflows and reports workflow steps the design gives no home, or carries out in a different order or by a different actor. Each design capability section names the workflow steps it carries out.

## 0.1.6 (2026-11-06)

- Requirements list scope (Avi, Nov 6): the Scope column's values are In SOW and Beyond SOW (was Past SOW), in every skill, story footer ("Priority: Beyond SOW") and the discovery call's start card. A new Scope decision column sits right of Scope with Raised with PM, Change order, Future phase and Dropped; empty on a Beyond SOW row means not yet reviewed. The discovery call writes Beyond SOW rows with Scope decision empty and lists the undecided ones on its report for the PM. The SC or PM fills Scope decision; Claude never fills it unless told what was decided.
- Conflict is a new Status value. When a call contradicts an earlier row or a closed decision, the discovery call sets the row to Conflict, keeps the earlier statement, adds the new quote under it and opens the blocking open item as before. When the SC settles it, the row goes back to Heard or Confirmed with the statement updated. Reports list the rows in Conflict.
- Readout: nothing is finalized and no sign-off is recorded while a requirement row is in Conflict; the skill lists them and stops. Before sign-off it lists every Beyond SOW row with its Scope decision for the PM and flags any still empty.
- Columns are found by header name, not letter ("the User stories column", not column Q). The discovery call reads the Requirements header row first; on an older sheet (Tog's, for one) it inserts a missing Scope decision column with its dropdown, renames Past SOW values to Beyond SOW, adds Conflict to the Status dropdown, and says so in the report.

## 0.1.3 (2026-11-02)

- Discovery call (Avi, Nov 2): the call is written straight into the four discovery documents, and the SC reviews it in the documents themselves (editing the requirements list directly, commenting on the workflow document and the What we heard page). "Fold in my comments" applies the comments, replies on each and resolves it, and the next run folds in any left open. Three kinds of change are never written silently: a conflict adds the new quote beside the old one and opens a blocking question instead of replacing anything; Past SOW items are written but tagged and listed for the PM; session adds, moves, splits, merges, cancellations and attendee changes stay suggestions. The SC's own edits in the sheet always stand. In Claude chat the report is a card (`references/start-card.html`): what needs the SC's eyes, then each document with its link and what moved, with buttons to fold in comments, draft the client follow-up email or draft the next session's agenda.
- Start card: items can link (`url`); the found block, the "not here" line and the summary take their own headings (`okTitle`, `naTitle`, `badTitle`, `sum`).

## 0.1.0 (2026-10-30), first build, not yet released

Skills built from the skill texts embedded in the live Start Motion page (version 1793311819-6881, Oct 30, 2026), one skill per stage command, with these additions on every skill:

- A Start section: the skill reads `references/method.md`, looks before it asks, and reports where the client stands against the stage's readiness list (the "Before you build" checklists on the page become what the command checks on open). A command that finds the client's documents missing offers to set them up right there.
- A one-message intake that works like the page's builder: the slide list (kickoff) and the section list (readout) shown in full with the optional items marked; the person answers once; the skill reads it back in one line, then shows the plan and waits, as the page does. No preset standard set. The readout's two settings (what we heard played back or future state only; dates solid or not) come prefilled from the Discovery documents note and can be changed.
- `references/method.md` per skill: what the stage is for, the checks before you accept, the bar, the calls the skill cannot make, and the link to the stage on the Start Motion page.
- A Next line at the end of every report naming the command that follows.
- The standing lines people used to paste from the page prompts moved into the skill's rules.
- Templates, logos and scripts carried inside each skill: discovery page templates and logos (discovery-plan, discovery-call), the readout template, build script and content example (readout), the kickoff slide templates, manifest, icons, brand files and tokens (kickoff), the Discovery documents note shape (discovery-call).
- The run log row names the plugin version.

- Shared outputs (Avi, Oct 30): the skills keep working out of the SC's Claude Project, and also save three things into the client's Drive folder (the Discovery subfolder, next to the requirements list) as they are written: the Discovery documents note as a Google Doc, every session note, and the readout sign-off record. The discovery call and user stories skills read those Drive copies when the project copy is not there, so anyone on the client can find the outputs.

- New client setup (Avi, Oct 30): `/start-motion:new-client` sets a client up once before the first stage: finds the signed SOW and whatever sales shared, finds or makes the client's Drive folder and its Discovery subfolder, says whether the person is in a Claude Project for the client (strongly recommended, not required) and which connectors are missing, offers the discovery documents setup, and names the first stage. The stage commands point to it when nothing at all exists for a client. The Start here page on Start Motion is the page version of the same steps, with the one-time install.
- Sales handoff (Avi, Oct 30): the kit assumes delivery gets the SOW plus whatever sales shared; no named sales calls folder and no transcript expectation. The discovery plan skill and the Discovery documents note no longer name a Sales Notes folder.
- The reading rule across the kit (Avi, Oct 30): the handoff, kickoff, discovery plan and discovery call skills read the whole client folder, every subfolder included; "01. Sales Handoff" is gone with "Sales Notes"; the readiness reports say what is there beyond the SOW in one clause instead of listing a handoff packet or transcripts as missing (`scripts/edits_0_2_0.py` is the record).
- Handoff is optional (Avi, Oct 30): it runs when sales shares a packet beyond the SOW; a folder holding only the SOW is reported as "nothing to hand off yet" and the skill stops; nothing downstream waits for it. The skill, its method reference and its description say so, and the handoff doc is saved in the Discovery subfolder, never at the top level. new-client hands back the text for the client Project's instructions.
- The em dash check in `build-readout.py` is written as a Python escape so the file carries none.
- Project instructions cut to three lines (Avi, Nov 2): the block new-client hands back now carries only the client, the Drive folder and the plugin line. The Kicksaw team, the client contacts and the document links were never read from the instructions; every stage reads them from the client folder and the Discovery documents note.

Commands: `/start-motion:new-client`, `/start-motion:handoff`, `kickoff`, `discovery-plan`, `discovery-call`, `readout`, `design`, `user-stories`.

Known gaps in this build: the kickoff brand folder has no topographic pattern PNGs (they live in the Kicksaw Slides design system; the skill builds without the pattern when it cannot read them). The kickoff icons were regenerated from Font Awesome Free (the same source the design system used), white on transparent, 256 px.
